## Replay a request range

Run commands from the repository root. A dry run reads local files and sends no requests:

```bash
RUN=play_runs/2026-10-03_Codex_Normal_API
node "$RUN/replay.mjs" "$RUN/calls.jsonl" --from=57 --to=68 --dry-run
```

For an actual future run, start the repository's official API play launcher with a fresh profile and descriptor. Keep its authentication files private. Set `BOKEMO_PLAY_DESCRIPTOR` to the authorized launcher's descriptor JSON, `BOKEMO_CLIENT_STATE` to a private client-state path, and `BOKEMO_RUN_DIR` to a **new** output directory. `client.mjs` obtains the endpoint/token from the descriptor and tracks session tokens/revisions privately.

```bash
export BOKEMO_PLAY_DESCRIPTOR=/tmp/next-bokemo-run/descriptor.json
export BOKEMO_CLIENT_STATE=/tmp/next-bokemo-run/client-state.json
export BOKEMO_RUN_DIR=/workspace/Kemo-Expedition/play_runs/next-normal-run
node "$RUN/replay.mjs" "$RUN/calls.jsonl" --user=NextNormalAccount
```

The original recording contains signup and login. A range starting later requires an authenticated client state and matching inventory/build/unlocks. Errors are omitted by `replay.mjs`. It regenerates each commit's `expectedRevision` and `idempotencyKey`. Random drops and gate outcomes vary: whole-run replay is a benchmark input sequence, not an adaptive winning strategy. Do not run the original exact HTTP bodies against a current account.

Generic parameter batches use an array of `{route, parameters, label}` and can run with:

```bash
node "$RUN/client.mjs" --batch plan.batch.json
```

## Automatic equipment tests

The concrete example compares Kemo's vitality armor with an owned tier-8 shield. It first validates the original slot and replacement inventory, measures two 1,000-run API forecasts, replaces one occupied slot in one commit, and restores the original armor in `finally`.

```bash
node "$RUN/equipment-test.mjs" "$RUN/equipment-tests.shield-vs-hp.json" --dry-run
node "$RUN/equipment-test.mjs" "$RUN/equipment-tests.shield-vs-hp.json"
```

The dry run needs no descriptor. The actual example needs the matching final party/inventory and an authenticated session. It uses six requests: two precondition reads, two forecasts, one replacement and one restoration. No elapsed-time commits are in the plan. This example was **not executed** after the victory; its proposed changes have no claimed performance result.

`equipment-test-results.json` records candidate forecast outcomes, seed domains, total experiment duration, and each measured request input/duration/response reference. Candidate steps apply cumulatively. Supply complete steps for each desired loadout or explicit resets between candidates. Once mutation steps are attempted, the final `restoreSteps` are attempted after the candidate loop, including on failure; restoration failures are recorded and surfaced. Forecast seeds differ, so tiny changes need more than one sample. `equipment-tests.example.json` is a read-only two-sample baseline template.

Plan shape:

```json
{
  "partyNumber": 1,
  "numberOfRun": 1000,
  "candidates": [
    {"name": "baseline", "steps": []},
    {"name": "candidate", "steps": [{"route": "/commit/build/character/1/equip", "parameters": {"targetEquipment": "0/8103/3/0", "targetSlot": 3}}]}
  ],
  "restoreSteps": [{"route": "/commit/build/character/1/equip", "parameters": {"targetEquipment": "0/1401/3/0", "targetSlot": 3}}]
}
```

Optional `preconditions` accepts `equipment` entries `{characterId,slot,item}` (the original item/jewel string without its slot prefix) and `ownedItems` entries `{item,quantity}`. Use checks whenever restoration relies on a particular original slot. Stop elapsed progression during a comparison so SEMI equipment changes do not invalidate the experiment. A failed precondition stops before equipment changes.

## Progression and offline search tools

- `control.mjs`: `party`, `items`, `exp`, `sim 1000`, `step N`, `advance N` (one day per iteration), `half N` (half-day per iteration). It stops D8 when only optional Gods gates remain. `opening` is for a fresh account.
- `build-twin.mjs` / `twin-entry.ts`: bundle the checkout's native engine into `/tmp/bokemo-codex-exp8/twin.mjs`, using esbuild. Run `node "$RUN/build-twin.mjs"` before offline optimisation after a workspace restart.
- `optimise.mjs`: reads the public `party.json`, `expedition.json`, `items.json`, `jewels.json`; evaluates fresh reconstructed parties, then writes `candidate.json` and `equipment.batch.json`. No API calls. `REFINE_ITERATIONS`, `ORDER_SWEEP`, `BUILD_SWEEP`, `DEITY_SWEEP` enable additional searches. `TARGET_FLOOR` changes only the offline gate scenario and must be labelled hypothetical.
- `boss-order.mjs`: compares six formations for boss-entry success and a hypothetical open-boss-gate scenario; writes `boss-order-search.json` and an optional one-call order batch.
- `apply-candidate.mjs`: applies the generated equipment and jewel batches, recording all API calls. It returns cross-character equipment before equipping and reads current slots before jewel attachment. It still rebuilds entire changed characters; use targeted replacements for a smaller future call budget.
- `finalize-record.mjs`: regenerates summary, exact recorded batch, portable successful batch, CSV and stage batch timings from the original ledger and final evidence. It sends no requests.

The search code is tied to this checkout/version and its public DTO shape. Archive names `dN-rREV-*.batch.json` contain the actual applied inputs; `*-offline-search.txt` contains the corresponding forecasts. Offline search rates are estimates, not observed live victories.

Credentials and authentication headers are absent from these artifacts. For the current session, the private profile/descriptor/client-state live under `/tmp/bokemo-codex-exp8`; preserve that directory if continuing the account. The Electron API runtime was left running.
