## Tips for another AI

1. **Read the reports, then freeze a written opening concept before signup.** Reuse their first-strike snipers and two-support core, but forecast your own owned variants. Projecting the old best final loadout onto this account's inventory made the fifth-floor forecast worse.
2. **Forecast the actual blocked gate and the correct outcome.** While a gate is closed, optimize successful Return. Once the boss is reachable, optimize Clear over the entire route. A full-HP single-boss test misses the damage accumulated on the way there.
3. **Treat consecutive-success gates as a probability problem.** A seemingly playable 8% Return rate can still make a three-success streak very slow. Diagnose the failing rooms rather than spending many days unchanged.
4. **For this D8 fifth-floor wall, test caster initiative.** A fast Ninja/Wizard Cervin with Nimble improved independently measured Return from 11.1% to 17.23%. Sniper Ninja/Ninja changes alone did not solve this stage. Test the caster with legal magic equipment, not an automatic physical Ninja loadout.
5. **Retest formation jointly with the build.** Laika behind two front snipers helped an earlier gate; Laika ahead of them was better with the new caster. Command, Defender, accuracy by row, and initiative interact.
6. **Preserve good variants and jewels.** Check new free jewels before rebuilding everyone. Allocate the strongest damage jewels where those characters are likely to act before the threatening enemy. Confirm proposed improvements with an independent seed and a larger sample.
7. **Clone parties and character arrays for every offline trial.** The native HP computation caches by array identity. Mutating the same array across trials can produce an invalid HP forecast. Keep unique characters' race, lineage, and predisposition fixed; validate every item category and owned count before API writes.
8. **Use exports carefully.** One backup supplies inventory, party, jewels, gates, and level, but its revision is in the response header. Refresh after live changes before applying an old candidate. Infer missing tier metadata from the item ID in this native-save planner, or use canonical item metadata.
9. **Check sortie availability, not stock alone.** A charge does not make an exhausted party eligible. Read `controls.sortie.available` or stop immediately after a losing instant sortie; an extra rejected call provides no benefit.
10. **Use the right completion evidence.** `godEntry` means the boss has not yet been defeated; `godGate` indicates a boss defeat, and an empty gate list can mean the optional gods battle is already available. Verify the boss flag or public difficulty ceiling. A latest outcome of Defeat can coexist with an earlier boss victory inside the same elapsed batch.
11. **Protect victory evidence before the boss.** Use short final increments and retain the winning sortie log immediately if available. The default diary settings in this attempt did not preserve the winning Clear. Do not promise an exact kill time based only on a later observation.
12. **Make request sequences fail fast.** Validate the whole build, perform it sequentially, and do not advance time if a mutation failed. Keep login payloads separate from signup payloads. Do not add guessed fields such as `limit` to strict API projections.

## Opportunities for future runs

- **Test the faster caster earlier.** At the fifth-floor wall, compare ordinary caster and Ninja/Wizard builds from the first frozen checkpoint. This attempt spent 6.5 days between first reaching that gate and observing it open. The discovery came late.
- **Use a two-stage optimizer.** Search inexpensive class/formation/jewel changes first; reserve full equipment reconstruction for large, independently confirmed gains. Rank candidates by expected game-time saving and the actual number of required API mutations.
- **Expand the caster search space deliberately.** The initial class sweep covered Wizard, Alchemist, and Sage combinations, so it missed Ninja/Wizard. Fill new slots and preserve the intended attack type in every class trial.
- **Pause progression when a streak is one success short.** The day-42.5 observation showed 2/3 at the fifth-floor gate, but a multi-day loop continued. A stored instant attempt might have helped; this is an untested opportunity, not a claimed saved victory.
- **Improve the harness before benchmarking.** The stale-revision incident cost 1.5 game days, and an empty-caster planner mistake persisted during D7. Repairing the planner after those mistakes cannot recover that time.
- **Measure uncertainty and route attrition.** Select on a common seed, confirm on an independent seed, and require a useful gain beyond sample noise. Optimize full-route boss Clear rather than a surrogate single-room score. Compare future openings across multiple fresh accounts rather than declaring a global optimum from one run.
- **Plan the evidence and stop rule before the end.** A one-room final sortie can preserve exact proof if the party is eligible; otherwise use shorter elapsed increments and inspect the boss flag immediately. Preserve the first successful battle separately from a rotating diary.

## Bugs, mistakes, and suggested improvements

### Observed API/session failure

After roughly twenty minutes of offline work/idle time, the automatic login renewal did not return an HTTP response. The original request eventually reported `UND_ERR_HEADERS_TIMEOUT`; a second overlapping login attempt was interrupted. No elapsed request was issued by either process. Restarting the official API session with the **same user-data profile** recovered revision **436** and exactly the same day-38 clock. Calls 537–538 are explicitly recorded as unanswered attempts.

The cause is unconfirmed; this is a reproducible symptom in this session, not a proven combat or login-lock implementation bug. Suggested improvements: bounded server-side login completion/error responses, cancellation handling, and clearer lease-renewal diagnostics. The client now applies a thirty-second request timeout and records unknown outcomes. A timed-out commit must be reconciled before retrying, not assumed to have failed.

### Client/planner mistakes encountered

| Call / issue | Effect and repair |
| --- | --- |
| 79: stale revision after backup | Client ignored the export revision header; a later progression chain continued with the old build. Fixed header parsing and revision refresh. About 1.5 game days were wasted. |
| 221: invalid login field `language` | Signup fields were reused for login. Fixed the payload to the login schema. |
| 276: incompatible Guardian equipment | Vitality swap chose a gauntlet Laika could not equip, after earlier removals had succeeded. Re-exported the actual state, repaired it before progression, and added compatibility preflight. |
| 328: deity already assigned | Fertility was held by a side party. Freed its assignment before applying the main-party candidate; added deity occupancy checks. |
| 580: unsupported diary field `limit` | Guessed a pagination field. Retried with the documented `partyNumber` only. |
| 587: exhausted instant sortie | Repeated a sortie after Defeat despite remaining stock. Availability must be checked independently of stock. |
| Empty caster and missing high-tier items | The forced-element planner could leave a caster empty when no preferred elemental item was available; native save items also lacked the assumed `tier`. Added elemental fallback, role/category filtering, and tier inference. |
| HP cache and marginal search scores | Reused mutable arrays risked stale HP; small-sample candidates could look stronger than confirmation results. Used fresh clones and larger independent comparisons. |
| Misread `godEntry` | Prematurely interpreted it as a cleared boss, then corrected the statement after checking the difficulty ceiling and source rules. Continued play until the boss flag was actually set. |

These HTTP validation rejections behaved correctly; they are **not game bugs**. No confirmed combat-engine bug was found.

Useful API/product improvements would include an atomic party-build transaction with dry-run validation, batched jewel edits, an explicit `bossDefeated` field in the expedition projection, and retention of the first boss victory with its timestamp/log regardless of item-drop triggers. These would reduce partial-build recovery costs, remove ambiguity around `godEntry`, and make API run verification more reliable.
