## Bugs / spec mismatches

1. **Spec example rejected: `mainClassId` in 9.1.3 §3-3-2.** The example `class.fighter` (and `subClassId: class.ranger`) is invalid. The API accepts only bare IDs (`guardian`, `duelist`, `ranger`, …), as listed in `validOptions.mainClassId` and used in the Opening guide. `class.guardian` is also rejected (`invalid_request:mainClassId`). §2-6-1 `enemyEditPane` still documents `class.`-prefixed IDs for a different endpoint, so the convention is inconsistent across sections. `fighter` is not a valid class at all.
2. **`simulationRun` detail lists rooms that are not reachable.** With destination 3f-3 blocked by the 2f-4 gate (`reachable: 2f-3`, `blockedByGate.floorRoom: 2f-4`), `detail` still contains a `2f-4` row with Success 97.1%. It should be omitted or shown as Not reached 100%. Also the response is far larger than the 9.1.3 §2-2-3 contract (`rooms[]` with HP histograms, `totals`, `seedDomain`, …); the JSON exceeds 6 KB, which broke a client that truncated output.
3. **Changing `destination` keeps the previous `depthLimit`.** After Dungeon 1 was cleared with `depthLimit: all`, setting `destination: 2` kept `all`. The forecast was safe here (1f-3 reachable, 1f-4 gate 0/7), but a client that assumes the limit resets will silently allow the deepest reachable room in the new dungeon as gates open. Documenting this in 9.1.3 §3-2-1, or exposing the limit in `compact`, would avoid surprises.

## Inconvenient features

1. **Sortie and `elapsed` results are nearly opaque.** `sortie` returns `outcome`, `rewards`, `logId` but no XP gained, rooms completed, gold change or level-up. `elapsed` returns only seconds and `inGameTime` — no cycle count, outcomes, rewards, gold, XP or level change. A client must call `compact` (which also runs 100 simulations) after every step to learn anything. Adding a compact summary (`cycles`, `outcomes` count, `experienceGained`, `goldDelta`, `levelBefore/After`, `unreadDiaryDelta`) to `effects` or `data` would remove most follow-up reads.
2. **Boss Rare diary entries omit the item.** `diary.event.bossRare` has `args: {}` and the title has no item name (the 9.1.3 compact example shows `Boss Rare acquired (Moon-Hare Aegis)`). Finding the item requires `latestBattleLog?logId=diary:<id>`, a 61 KB response. Item and enhancement should be in the entry `args`.
3. **`clearGates` shape is uneven.** `eliteGate` has `floor`; `bossGate`, `entryGate` and `godEntry` return `floor: null`. Gate name is only implied by `kind`+`floor` (the "3rd Elite gate" is `floor: 4`), which is easy to misread. The UI spec (8.3) even shows different required counts (`0/9`) from 5.1 (7 / 6 / 5 / 4 / 3).
4. **Shop is a poor gold sink and paid refresh is a trap.** Every lineup is 60G tier-1 commons; a paid refresh costs 200 → 400 → 800 → 1,600 (doubling) and returned only 11xx items in three consecutive refreshes. After a few days the inventory held 50–99 copies of each such item, so the shop had no use. There is no preview of the next price beyond `paidRefreshPrice`, and nothing warns that stock quality is unchanged. Gold has no in-API sink other than the shop, and donations are automatic and read-only (`donationBox`).
5. **`sellInventoryItems` always sells the whole stack and turns the variant to auto-sell.** Correct per 9.1.4, but I sold 82 copies of 1101 in one call while trying to sell "some". There is no `keep` quantity, no dry-run and no way to sell one unit; auto-sell then silently applies to all later drops of that exact variant (it is why Gold started rising). A `simulation:true` mode like `changeBuild` (or a quantity field) would prevent accidents.
6. **New purchases are not equipped in FULL mode until Auto Equipment runs.** After buying armor 1101, characters kept their empty slots and `emptyEquipmentSlot: ["2/2"]` stayed. An explicit `autoEquipment` with `immediateAutoEquipment: true` was needed on each of the 6 characters (one call per character, six revisions). A party-wide immediate run would save calls.
7. **`compact` observation is heavy for frequent polling.** It runs 100 simulations per call (documented) and omits gates, depth limit and next objective, so a loop needs `compact` + `observation/expedition` + `simulationRun` for one decision. Adding `depthLimit` and the current gate to `compact` is cheap.
8. **`lineup_changed` is used for a malformed `lineupId`** (`"nope"`). It should be `invalid_request` for shape errors; `lineup_changed` should mean a valid but outdated ID.
9. **`changedResources` names only `read/observation/*` projections.** After `autoEquipment` or `removeAllEquipment` it lists `read/observation/party` and `read/observation/base`, never the per-character reads (`read/build/character/{id}/equipment`) that a client actually needs to refresh; the commit `data.current` happens to carry the new equipment, but `changedResources` does not tell a client which character changed.
