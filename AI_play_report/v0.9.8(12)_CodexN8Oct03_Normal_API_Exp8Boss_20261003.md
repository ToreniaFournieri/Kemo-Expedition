## Advice for another AI

1. **Start with first-strike snipers and two support tanks.** The prior reports' ninja/ranger, lord/lord, guardian/guardian opening worked here. Use strong arrows/bolts together with bows that supply attack count and accuracy. Keep the main party on a fixed destination, `all`, offset 0 while clearing gates.
2. **Use the actual gate scenario.** A forecast for D8 floor 1 is not a forecast for floor 2. Read `depthLimit.reachable` and `blockedByGate` from `simulationRun`. Each gate needs consecutive successful Returns and resets on a failed run. The first D8 search here had an 85% first-floor forecast; it did not justify waiting at the harder second-floor gate without another snapshot.
3. **Optimize the streak probability, not a stat total.** For success probability p and a streak of k, expected trials are `(p^(-k) - 1) / (1 - p)`. For k=3, p=0.08 means about 2,122 trials; p=0.25 means 84. Raising a poor success rate can save much more time than skipping one optimization. Actual waiting time varies greatly.
4. **Use a changing seeded random stream offline.** Fill every element requested by `crypto.getRandomValues`; do not return the same seed for every battle. An early constant-seed mistake produced misleading perfect forecasts in this run. Compare candidates on common random numbers, then validate with a different seed. Several 400-trial selections here fell substantially in independent validation; use more trials before committing a marginal winner.
5. **Use canonical HP and stat computation.** Vitality growth, effective character level, item enhancements, class multipliers, and deity effects make a simple HP proxy unreliable. Use `computeCharacterHpContribution` and `computePartyStats`, then evaluate complete expeditions. More HP or defense alone was often worse here.
6. **Test elements and formation together.** D7 favored fire; D8 favored thunder because of Voidspawn resistances. Filter incompatible direct elemental weapons during a structured build. Test both tanks in front and Command in front with snipers on rows 2–4. D8 floor 4 benefited from the latter; the final party returned both tanks to rows 1–2.
7. **Query jewels explicitly and reserve unchanged characters' property.** Item searches without `category=jewel` omit jewels. Distinct ranks stack on one character; duplicate ranks of the same type do not. For a caster-only test, available jewels are free jewels plus the caster's attached jewels, not the entire party's collection. The first caster-tuning implementation duplicated tank jewels in its candidate; its initial report contains an invalid plan and should not be used as a legal benchmark. `caster-recovered-validation.json` records the corrected D7 build, and the current tuning scripts reserve unchanged equipment and jewels.
8. **Reduce mutation calls before the first rebuild.** Compare item multisets, preserve unchanged slots and jewel-bearing duplicate copies, use one-slot `equip` replacements, or one `removeEquipment` call with a slot list followed by an `equip` array containing only added items. Equip/remove responses provide authoritative slot addresses, so another party read is usually unnecessary. The final helper implements this, but the earlier 148 full removals and many jewel reattachments already inflated this run's call count.
9. **Choose snapshots according to the metric.** An API backup captures exact party, inventory, jewels, gates, and other state in one call. It is convenient for an offline twin and a replay checkpoint. Here export median time was 603 ms; party reads were about 39 ms and item searches about 7 ms. Exports save calls but transfer more data and can take longer. Reuse a frozen checkpoint for multiple offline searches instead of exporting again. Backups do not preserve the API control lease or live RNG stream.
10. **Rebuild for significant new drops, not every half day.** `SEMI` upgrades existing equipment variants, but new slots and new item IDs still merit a deliberate pass. At the fifth-floor wall, several small tests produced no substantial gain; newly available jewels and enhancements eventually doubled the forecast. Keep useful independent tests offline and commit the winner once.
11. **Use the documented request shape.** The forecast input is `{ "numberOfRun": 1000 }`, not `times`. Keep revision and idempotency fields current. The 15-minute idle lease did not expire here because API activity resumed between offline batches; one login sufficed.
12. **Prove the boss kill directly.** A `bossRare` Diary trigger alone is insufficient: some elites can drop items in that rarity range. Retrieve the retained log and check `finalOutcome: Clear`, room 24 `battle_Boss`, and enemy 387. Save the native boss-defeat flag and the unlocked difficulty range as corroboration. Stop advancing time once victory is established.
